# RCV-020 Observatory / Radar / Ingestion Implementation Design V1

## 1. Design status and authority guard

This document translates the frozen RCV-020 Contract V1 into an
implementation-ready physical and service design. It introduces no semantics
beyond that Contract.

The frozen Contract is:

`docs/provenance/rcv020-observatory-radar-ingestion-contract-v1.md`

Its required SHA256 is:

`ff3deb8607767e4a7bdf3668b6d0370ba7694de734262f28bfdda879b8090d62`

An implementation must verify this hash before applying this Design. A hash
mismatch is a hard stop.

## 2. Architectural boundary

The implementation pipeline is:

`LogicalSource → Monitor → MonitorConfigurationVersion →
ObservationOccurrence → RetrievalAttempt → Capture → comparison/revision →
coverage projection → AuthenticatedHandoff → downstream evidence ingestion`.

The system may create an optional research-trigger request, but RCV-020 does
not execute research or make an evidential judgment. RCV-019 remains the
authority for later temporal evidence-state evolution.

Historical reads use persisted RCV-020 records and authenticated retained
artifacts only. They never consult the current endpoint, current source page,
current monitor configuration, current adapter/parser installation, or mutable
current raw-object availability as a substitute for historical authority.

## 3. Physical entity set

The authoritative relational entities are:

1. `logical_sources`;
2. `monitors`;
3. `monitor_configuration_versions`;
4. `configuration_lifecycle_events`;
5. `observation_occurrences`;
6. `observation_occurrence_resolutions`;
7. `retrieval_attempts`;
8. `retrieval_attempt_resolutions`;
9. `captures`;
10. `capture_comparisons`;
11. `quarantined_payloads` (diagnostic only, never Capture authority);
12. `retention_availability_events`;
13. `authenticated_handoffs`.

`research_trigger_requests` is intentionally not persisted in RCV-020 V1.
The Contract makes it optional, and omitting it keeps the observation
authority boundary minimal. A future Research Orchestration RCV can attach a
request to immutable Capture/Occurrence identities without rewriting them.

Coverage is derived from occurrences, attempts, configuration lifecycle, and
evaluation records. Mutable aggregate coverage rows are not authoritative.

All authoritative tables use UUID primary keys generated by the write path.
Every authoritative row has `created_at` and a deterministic canonical/hash
where stated below. Authoritative rows are append-only and protected against
UPDATE and DELETE by database triggers.

The relational relationship and index matrix is:

| Entity | Parent FKs and cardinality | Required uniqueness/indexes | Historical role |
| --- | --- | --- | --- |
| `logical_sources` | none | identity hash unique; class/jurisdiction indexes | stable source identity |
| `monitors` | one LogicalSource; many per source | source index; identity hash unique | endpoint relationship identity |
| `monitor_configuration_versions` | one Monitor; many versions | `(monitor_id, version_number)` unique; monitor/effective-time index; deferred overlap check | exact configuration authority |
| `configuration_lifecycle_events` | one configuration; many events | `(configuration_id, event_sequence)` unique; configuration/time index | activation, retirement, pause, resume |
| `observation_occurrences` | source, monitor, configuration | source/monitor/config/time indexes | expected or triggered work identity |
| `observation_occurrence_resolutions` | one occurrence; exactly one terminal row | `occurrence_id` unique; outcome/time indexes | immutable terminal outcome |
| `retrieval_attempts` | one occurrence; optional prior attempt | `(occurrence_id, retry_number)` unique; occurrence/time index | immutable attempt start and retry lineage |
| `retrieval_attempt_resolutions` | one attempt; exactly one terminal row | `attempt_id` unique; outcome/time index | immutable attempt outcome/failure |
| `captures` | one successful attempt; one occurrence/configuration | attempt unique; content hash and observed-time indexes | observed representation authority |
| `capture_comparisons` | current capture plus optional prior capture | current-capture unique; prior-capture/time indexes | deterministic change result |
| `quarantined_payloads` | failed attempt only | attempt/time/hash indexes; no Capture FK | non-authoritative diagnostics |
| `retention_availability_events` | one Capture; many events | `(capture_id, event_sequence)` unique; capture/time index | immutable availability history |
| `authenticated_handoffs` | one Capture and attempt lineage | idempotency key unique; capture/time index | downstream-ingestion authority |

All parent FKs are `ON DELETE RESTRICT`/`NO ACTION`. Child indexes are created
for every FK used by reconstruction. Every matrix row except quarantine is
covered by the immutable-history trigger policy; quarantine is also append-only
but has no path to satisfy Capture or Handoff authority.

## 4. LogicalSource

`logical_sources` contains the stable identity of the real-world publishing or
source entity, not a trust judgment.

Required columns:

- `logical_source_id uuid primary key`;
- `organization_identity text not null`;
- `source_class text not null`;
- `jurisdiction text null`;
- `created_at timestamptz not null`;
- `identity_canonical jsonb not null`;
- `identity_hash bytea not null`.

Display labels and descriptive metadata are informational and must not become
historical identity. Changes are represented by a new versioned configuration
or future append-only metadata authority, never by changing the source ID.

Constraints include non-empty identity fields, canonical/hash validation, and
unique identity hash. There are no trust, credibility, official-status, or
truth columns. Indexes cover `organization_identity`, `source_class`, and
`jurisdiction`.

## 5. Monitor

`monitors` represents one endpoint/retrieval relationship belonging to one
LogicalSource.

Required columns:

- `monitor_id uuid primary key`;
- `logical_source_id uuid not null references logical_sources`;
- `monitor_kind text not null`;
- `created_at timestamptz not null`;
- `identity_canonical jsonb not null`;
- `identity_hash bytea not null`.

The endpoint itself belongs to MonitorConfigurationVersion, not to mutable
Monitor state. RSS and API monitoring of one LogicalSource are separate
Monitors. Endpoint replacement creates a new Monitor when the retrieval
relationship changes materially; it never replaces LogicalSource identity.

Foreign-key deletion is `RESTRICT`. Monitors are immutable. Indexes cover
`logical_source_id` and identity hash.

## 6. MonitorConfigurationVersion

`monitor_configuration_versions` is immutable configuration authority.

Required columns:

- `monitor_configuration_version_id uuid primary key`;
- `monitor_id uuid not null references monitors`;
- `version_number bigint not null`;
- endpoint/request target and canonical request fields;
- `retrieval_method text not null`;
- `authentication_reference text null`;
- expected media/content constraints;
- cadence or external/operator trigger eligibility;
- jurisdiction/language/geographic/topic scope;
- safety and access-policy limits;
- adapter identity/version;
- parser identity/version where capture-side authoritative;
- retention policy/version;
- `effective_from timestamptz not null`;
- immutable declared/evaluated effective interval authority;
- `created_at timestamptz not null`;
- `canonical jsonb not null` and `canonical_hash bytea not null`.

Secrets and tokens are excluded. Authentication references identify a protected
secret/configuration outside the historical canonical payload.

`version_number` is positive within the PostgreSQL BIGINT domain. The driver
reads it as exact decimal text (or explicit `BigInt`) and never converts it to
a JavaScript Number; no global driver parser is changed.

There is a unique `(monitor_id, version_number)` constraint. Configuration
interval authority is reconstructed as half-open intervals
`[effective_from, effective_until)` from lifecycle events. A deferred
constraint trigger rejects overlapping active intervals for one Monitor,
including ambiguous same-time activation/retirement ordering. Parallel
endpoints use distinct Monitors, so their configurations may be active
concurrently.

## 7. Configuration lifecycle events

`configuration_lifecycle_events` is append-only and records:

- `event_id uuid primary key`;
- `monitor_configuration_version_id` FK;
- `event_type` enum: `ACTIVATED`, `RETIRED`, `PAUSED`, `RESUMED`;
- `event_at timestamptz not null`;
- actor or policy identity;
- reason and safe diagnostic metadata;
- monotonic per-configuration `event_sequence bigint`;
- canonical/hash.

Activation is exactly once per configuration. Retirement is at most once.
The exact state machine is:

`NOT_ACTIVATED → ACTIVE` via exactly one `ACTIVATED` event;
`ACTIVE → PAUSED` via `PAUSED`;
`PAUSED → ACTIVE` via `RESUMED`;
`ACTIVE → RETIRED` via `RETIRED`;
`PAUSED → RETIRED` via `RETIRED`.

`RETIRED` is terminal. WriteVerifier rejects duplicate activation, retirement
before activation, resume while not paused, pause while already paused or
nested, any event after retirement, malformed or decreasing event time, and
history that contradicts the immutable effective interval. ReadVerifier
independently rejects the same persisted corruptions with no repair or
normalization. Lifecycle rows cannot be updated or deleted.

Historical effective state is reconstructed by ordering lifecycle events by
`event_at`, `event_sequence`, and event identity, subject to the Contract's
overlap prohibition. Boundary equality is valid because intervals are
half-open: `[effective_from, effective_until)`. A current-active view may be
cached, but it is derived only and never historical authority.

## 8. ObservationOccurrence

`observation_occurrences` contains the immutable work identity before terminal
resolution.

Required columns:

- `occurrence_id uuid primary key`;
- LogicalSource, Monitor, and MonitorConfigurationVersion FKs;
- `trigger_origin` enum: `SCHEDULED`, `EXTERNAL`, `OPERATOR`;
- trigger-specific canonical authority and hash;
- `scheduled_at` for scheduled work, otherwise null;
- `trigger_received_at` for external work, otherwise null;
- `requested_at` for operator work, otherwise null;
- `due_at` where applicable;
- immutable evaluation policy/version and cutoff/deadline authority;
- `created_at`, occurrence canonical, and canonical hash.

`observation_occurrence_resolutions` is a separate append-only table with one
terminal row per occurrence:

- `resolution_id uuid primary key`;
- `occurrence_id unique FK`;
- `outcome` enum: `SUCCEEDED`, `FAILED`, `MISSED`, `SKIPPED`;
- `evaluation_cutoff_at`, `evaluated_at`;
- explicit skip reason/actor/policy when SKIPPED;
- terminalization policy/version and canonical/hash.

No `DISABLED` or `NOT_APPLICABLE` resolution exists. If no work was due, no
occurrence is generated; the configuration/scheduling event explains that
state.

## 9. RetrievalAttempt

`retrieval_attempts` records an immutable execution start. Required columns:

- `attempt_id uuid primary key`;
- `occurrence_id not null FK`;
- `previous_attempt_id null FK to retrieval_attempts`;
- positive `retry_number bigint`;
- `retrieval_started_at timestamptz not null`;
- `attempt_deadline_at timestamptz not null`, derived from the historically
  bound deadline policy/version;
- MonitorConfigurationVersion and adapter identity/version;
- deterministic redacted request/query canonical and hash;
- `created_at`, canonical, and canonical hash.

Unique `(occurrence_id, retry_number)` prevents duplicate retry lineage.
`attempt_deadline_at` must be no later than the parent occurrence evaluation
boundary. `retrieval_attempt_resolutions` is append-only, one terminal result per
attempt, and contains:

- `attempt_resolution_id uuid primary key`;
- `attempt_id unique FK`;
- `retrieval_completed_at`;
- `outcome` enum: `CAPTURED_CHANGED`, `CAPTURED_UNCHANGED`,
  `CAPTURED_EMPTY`, `FAILED`;
- failure taxonomy version and failure code when FAILED;
- safe diagnostic metadata/reference;
- canonical/hash.

An attempt may therefore be visible as started but unresolved while work is
in flight; no mutable update is needed to preserve its history. A row with a
`previous_attempt_id` is a Retry only when its predecessor belongs to the same
occurrence, has an immutable terminal `FAILED` resolution, and the retry starts
after that predecessor's terminal resolution. `retry_number` must equal the
predecessor number plus one, and the predecessor graph must be acyclic.
Speculative parallel attempts are not Retry authority in V1; WriteVerifier and
ReadVerifier reject them as invalid retry lineage.

## 10. Deterministic terminal resolution

Terminalization creates exactly one immutable occurrence resolution after the
configured evaluation boundary and any required grace/deadline processing.

- `SUCCEEDED`: at least one attempt has produced a valid Capture before the
  terminal boundary. Earlier failed attempts remain visible.
- `FAILED`: at least one attempt occurred, no valid Capture succeeded, and a
  classified failure reached terminal resolution.
- `MISSED`: zero attempts existed by the evaluation boundary.
- `SKIPPED`: execution was explicitly skipped before retrieval execution.

Every admitted attempt has an authoritative `attempt_deadline_at` no later
than the occurrence evaluation boundary. No admitted attempt remains
authoritatively in flight at that boundary. An attempt started before the
boundary but incomplete by its deadline terminalizes immutably as FAILED with
`TIMEOUT` when the deadline/timeout policy caused termination. Bytes or results
arriving after that deadline cannot change either resolution and cannot create
a Capture; they may be retained only as safely marked quarantine/diagnostic
material. A terminal occurrence can therefore never later become SUCCEEDED.

A failed attempt followed by a valid later retry, started after the failed
predecessor's terminal resolution and completed before the occurrence boundary,
may still resolve the occurrence SUCCEEDED. Terminalization uses persisted
cutoff and evaluation authority, not the time of a later read query.

## 11. Request/query authority

Request authority is stored with each attempt as a redacted deterministic
canonical plus hash. It includes method, target identity, relevant parameters,
adapter-visible request semantics, and configuration-version identity. Secrets
and tokens are replaced by stable credential-reference identifiers and are
never included in canonical bytes.

The same canonical request/hash is used to authenticate EMPTY results and as an
input to capture comparison. Redaction rules and canonical algorithm versions
are versioned authority.

## 12. Capture

`captures` is immutable and every successful attempt creates one distinct row.
Required columns:

- `capture_id uuid primary key`;
- LogicalSource, Monitor, MonitorConfigurationVersion, ObservationOccurrence,
  and RetrievalAttempt FKs;
- requested URL/query identity and hash;
- final URL and redirect manifest/hash where applicable;
- response/status metadata, allowlisted headers, media type, and byte length;
- `observed_at timestamptz not null`;
- content/representation hash;
- capture canonical and capture hash;
- original retention policy/version and raw-object identity/reference if
  retained;
- `created_at`.

Capture identity differs from content hash and blob/object identity. Identical
bytes may be physically deduplicated, but identical observations remain
distinct Capture rows and occurrences. Capture rows have no UPDATE or DELETE
path.

## 13. Raw object and blob boundary

PostgreSQL stores authoritative relational metadata, identities, canonical
forms, hashes, statuses, relationships, and retention events. Raw bytes and
large artifacts may be stored in immutable content-addressed object storage.

The object identity is derived from the content hash, algorithm, and storage
namespace, but is not Capture identity. For retention policies requiring raw
bytes, authority ordering is strict: receive candidate bytes; compute expected
hash and length; upload/write the immutable final object identity; independently
verify final existence, hash, and length; only then begin and commit the
PostgreSQL transaction that inserts the object reference, Capture, resolutions,
comparison, and Handoff rows. A committed Capture never references a pending,
unfinalized, or unverified object. A storage provider is not frozen by this
Design.

Quarantine objects use separate identities and storage/policy boundaries and
are never referenced by Capture or Handoff foreign keys.

If upload/finalization succeeds but the database transaction never commits, or
the transaction rolls back, the object is an unreferenced orphan and there is
no Capture authority. If the process crashes before commit, the same rule
applies. A committed transaction implies that required retained bytes were
already finalized and verified. If an object later disappears, the Capture
remains OBSERVED/AUTHENTICATED and an append-only `LOST` or availability event
changes only REPLAYABLE. Orphan cleanup may delete only objects proven
unreferenced by authoritative relational history; it must never delete an
object referenced by historical authority. Under `METADATA_HASH_ONLY`, no
object is required, but immutable hash, length, and metadata remain mandatory.

## 14. Retention and availability

`retention_availability_events` is append-only with:

- event identity;
- Capture FK;
- event type: `DELETED`, `EXPIRED`, `RESTRICTED`, `LOST`, or
  `AVAILABILITY_CHANGED`;
- reason and policy/legal basis where applicable;
- event timestamp;
- resulting availability semantics;
- event sequence;
- canonical/hash.

The original Capture retention policy/reference never changes. Current
replayability is derived from the Capture plus ordered availability events.
RCV-020 V1 does not define an authoritative transition from unavailable back
to replayable; restoration/reacquisition requires a future Contract decision.

## 15. Observed, authenticated, replayable outputs

The ReadVerifier computes:

- `observed = true` only when a valid Capture exists;
- `authenticated = true` only when all identity, provenance, canonical, and
  hash checks pass;
- `replayable = true` only when the authenticated raw object is currently
  available and hash/length validation succeeds.

These are derived verification results, not mutable historical booleans.
Availability events are the historical authority for why replayability is
currently false. A hash-only Capture is never reported replayable.

## 16. Empty and changed/unchanged comparison

An EMPTY result is authoritative only when the attempt has a valid request
canonical/hash, a successful adapter response envelope, and an adapter
versioned result proving zero items. Missing rows or absent content alone
cannot create EMPTY.

`capture_comparisons` contains:

- comparison identity;
- current Capture FK;
- prior Capture or source-revision FK when one exists;
- comparison algorithm identity/version;
- reproducible input hashes;
- result `FIRST_OBSERVED`, `CHANGED`, or `UNCHANGED`;
- canonical/hash.

Comparison is directional: `currentCaptureId → priorCaptureId`. The two
Capture IDs must differ, belong to the same Monitor, and the prior Capture's
authoritative `observed_at` must be strictly earlier than the current Capture's
value. Future references, self-comparisons, equal-time pairs, and comparisons
with missing algorithm/version authority are rejected. Exactly one comparison
row exists for a current Capture under the applicable algorithm/version when
CHANGED or UNCHANGED semantics require comparison. EMPTY does not invent a
comparison, and FAILED has no CaptureComparison.

The first representation is represented by `FIRST_OBSERVED` and the attempt
outcome `CAPTURED_CHANGED`. Authoritative UNCHANGED is limited to raw-byte or
deterministic representation equality. AI or semantic similarity is never the
authoritative comparison result.

## 17. Failure and parser boundaries

The V1 failure enum is:

`DNS_FAILURE`, `CONNECTION_FAILURE`, `TIMEOUT`, `HTTP_FAILURE`,
`AUTHENTICATION_FAILURE`, `RATE_LIMITED`, `UNSAFE_REDIRECT`,
`PAYLOAD_TOO_LARGE`, `UNSUPPORTED_MEDIA`, `MALFORMED_RESPONSE`,
`PARSER_FAILURE`, `CAPTURE_INTEGRITY_FAILURE`, `SOURCE_REMOVED`,
`ACCESS_RESTRICTED`, `CONFIGURATION_ERROR`, `INTERNAL_ERROR`,
`OTHER_UNCLASSIFIED`.

Each failed attempt stores taxonomy version, code, and safe diagnostic data.
`OTHER_UNCLASSIFIED` requires preserved diagnostics and is never a silent
historical remapping.

`PARSER_FAILURE` is limited to capture-side decoding/parsing/validation needed
to establish the observed representation. Later derived extraction, AI,
entity, claim, text, or summary failures are separate derived-operation
records and cannot invalidate a valid Capture.

## 18. Quarantine and rejected payloads

`quarantined_payloads` may retain bytes or metadata received by failed attempts
for security or operational diagnostics. This includes results arriving after
an authoritative attempt deadline. Such material can never change an
AttemptResolution, OccurrenceResolution, or create a Capture. It contains its
own identity, attempt reference, reason, policy, object reference, hash/length
when available, and retention events.

Quarantine has no Capture-parent or Handoff path. Unsafe, oversized,
malformed, unsupported, or integrity-failed data cannot satisfy Capture
foreign keys unless it independently passes Capture validation.

## 19. Coverage

Coverage is derived from immutable occurrences, attempts, resolutions,
configuration lifecycle events, and persisted evaluation cutoffs. A derived
view may expose:

`EXPECTED`, `ATTEMPTED`, `SUCCEEDED`, `FAILED`, `MISSED`, and `SKIPPED`.

For scheduled monitoring, EXPECTED is the count of occurrences due under an
active configuration within the requested interval. Retries do not increase
EXPECTED. DISABLED and NOT_APPLICABLE produce no occurrence and therefore no
fake expected work. SKIPPED remains visible in the denominator; FAILED and
MISSED remain distinct outcomes.

Coverage queries require an explicit immutable interval, evaluation cutoff,
grace/deadline policy/version, and source/monitor/configuration scope. Results
must expose transparent counts and never claim universal search.

## 20. Event-driven coverage

External occurrences are created only from externally received and accepted
event identity/receipt authority. Their coverage describes processing of those
received events. It does not use scheduled denominators and does not infer
undelivered upstream events.

Upstream delivery completeness is reported as UNKNOWN unless a separate
authenticated sequence, ledger, manifest, or delivery receipt establishes the
expected external event set.

## 21. AuthenticatedHandoff

`authenticated_handoffs` is immutable observation-side authority. Required
columns include:

- handoff identity;
- Capture identity;
- LogicalSource, Monitor, and MonitorConfigurationVersion identities;
- ObservationOccurrence and RetrievalAttempt identities;
- capture hash;
- immutable raw-object identity/reference and availability snapshot as known at
  handoff creation;
- observedAt;
- optional source publication metadata;
- source artifact identity where available;
- derived extraction reference/version/hash where used;
- provenance manifest;
- handoff canonical/hash;
- createdAt;
- deterministic `idempotency_key`.

The availability snapshot is a value captured at creation, not a live lookup.
Retention/Availability event IDs may be referenced. Later availability events
never rewrite the handoff.

The idempotency key is the canonical hash of Capture identity, downstream
ingestion namespace/target, handoff purpose/version, and applicable derivation
identity. When no derived extraction participates, the derivation component is
the explicit versioned canonical null sentinel `DERIVATION_NONE_V1`; an omitted
field, empty string, or mutable default is never equivalent. A unique
constraint prevents duplicate underlying evidence authority for the same
logical handoff. One Capture may still be linked to multiple Claims downstream.

## 22. Write verifier

The write verifier validates before persistence:

- all source/monitor/configuration identities and FK relationships;
- immutable configuration intervals and overlap rules;
- lifecycle transition legality, event ordering, and activation/retirement
  rules;
- timestamp canonicality and cutoff authority;
- attempt deadline legality, retry predecessor state/order, acyclicity, and
  unique retry number;
- valid terminal outcome combinations;
- Capture only for a successful attempt, with exactly one Capture per
  successful attempt;
- EMPTY only with request/query authority;
- UNCHANGED only with directional prior Capture and comparison authority;
- no self, future, equal-time, or cross-Monitor comparison;
- response/redirect/media/size/integrity policy;
- failure taxonomy/version;
- handoff identity, raw-availability snapshot, and idempotency key;
- duplicate same-identity canonical content;
- divergent same-identity content as an explicit conflict.

No write verifier path consults mutable current source state to complete an
historical record.

## 23. Read verifier

The independent ReadVerifier accepts only a reconstructed persisted bundle. It
has no database or network dependency and does not call current adapters,
parsers, endpoints, or object metadata APIs except to verify a separately
authenticated retained object when replayability is requested.

It reconstructs lifecycle intervals, occurrence resolution, attempt lineage,
capture identity, comparison authority, retention history, coverage facts, and
handoff authority from persisted records. It fails closed with deterministic
codes for at least:

`MISSING_DATA`, `MALFORMED_DATA`, `VERSION_MISMATCH`, `HASH_MISMATCH`,
`CANONICAL_MISMATCH`, `IDENTITY_MISMATCH`, `MEMBERSHIP_MISMATCH`,
`ORDERING_VIOLATION`, `CONFIGURATION_OVERLAP`, `INVALID_LIFECYCLE_TRANSITION`,
`LIFECYCLE_ORDERING_VIOLATION`, `DUPLICATE_TERMINAL_RESOLUTION`,
`ATTEMPT_DEADLINE_VIOLATION`, `RETRY_LINEAGE_VIOLATION`,
`INVALID_TERMINAL_OUTCOME`, `CAPTURE_PARENT_MISMATCH`,
`INVALID_COMPARISON_AUTHORITY`, `RETENTION_HISTORY_INCONSISTENCY`,
`HANDOFF_MISMATCH`, `UNSUPPORTED_STATE`, and `CURRENT_STATE_SUBSTITUTION`.

There is no repair, normalization, current-state fallback, or latest-version
fallback.

The ReadVerifier pairs every writer invariant with an independent persisted
corruption check: lifecycle state-machine legality and ordering; configuration
overlap; unique occurrence and attempt resolutions; attempt deadline and
in-flight legality; failed-predecessor retry ordering and acyclicity; Capture
parent/result parity and one-Capture cardinality; directional/self/future/
equal-time comparison rules and algorithm/version; retention event legality and
ordering; raw-object authority requirements; handoff identity and idempotency;
and canonical/hash/version integrity. Duplicate resolutions, retirement-before-
activation, resume-without-pause, nested pauses, late post-deadline results,
Capture attached to FAILED or unresolved attempts, and invalid comparison
direction all fail closed. Writer acceptance is never used as a substitute for
reader verification.

## 24. Atomicity and transaction boundaries

Each authoritative unit is persisted transactionally:

- configuration version plus its activation/lifecycle authority;
- occurrence plus attempt start/resolution;
- successful attempt, Capture, comparison, and handoff;
- quarantine and failed-attempt diagnostics where applicable.

For retained-raw policies, the object is uploaded to its final immutable
content-addressed identity and independently verified before the PostgreSQL
transaction begins. The transaction then inserts the verified object
reference, Capture, resolutions, comparison, and Handoff rows and commits the
relational authority. A failure at any meaningful relational stage rolls back
all new rows in that unit. Unreferenced finalized objects are permitted
orphans, are never Capture authority, and may be garbage-collected only after
an authoritative-reference check.

## 25. Concurrency

Database constraints are authoritative:

- unique configuration version number per Monitor;
- deferred non-overlap validation per Monitor;
- unique occurrence resolution;
- unique retry number per occurrence;
- unique Capture identity;
- unique comparison identity/current-capture relation;
- unique handoff idempotency key.

Concurrent processing of one occurrence may create distinct attempts only when
retry identities are distinct. Concurrent creation of the same retry or
handoff key yields one committed authority and a deterministic uniqueness
conflict, with failed transactions fully rolled back. Concurrent captures with
different Capture IDs may share content hashes. No application-only current
state check is authoritative.

## 26. Duplicate and idempotency behavior

- Same identity and same canonical content: exact duplicate is accepted only
  through the defined idempotency key; no second underlying authority is
  created.
- Same identity and divergent canonical content: reject with deterministic
  identity/conflict failure and roll back.
- Different identity and equivalent content: retain separate occurrence and
  Capture identities; comparison may report equality.
- Same Capture-to-target handoff key: deterministic idempotent result.
- Different target Claim references: allowed without duplicating Capture
  authority.

## 27. Immutability and referential actions

The following are strictly immutable and have database UPDATE/DELETE guard
triggers: LogicalSource, Monitor, MonitorConfigurationVersion, lifecycle
events, ObservationOccurrence, occurrence resolutions, RetrievalAttempt,
attempt resolutions, Capture, comparisons, quarantine records, retention
events, and handoffs.

Foreign keys use `ON DELETE RESTRICT` or `NO ACTION`. No cascade may remove
historical authority. Diagnostic object cleanup is separate from relational
history and cannot delete Capture or Handoff rows.

## 28. BIGINT and numeric safety

The only BIGINT fields in V1 are:

| Entity/field | Semantic purpose | Minimum | Maximum/semantic bound | Database check | Driver/canonical representation |
| --- | --- | ---: | --- | --- | --- |
| `monitor_configuration_versions.version_number` | Configuration revision order within one Monitor | 1 | PostgreSQL BIGINT maximum; no smaller semantic maximum | `version_number >= 1` and unique per Monitor | decimal string or `BigInt`; canonical decimal string |
| `retrieval_attempts.retry_number` | Retry position within one occurrence | 1 | PostgreSQL BIGINT maximum; additionally predecessor + 1 | `retry_number >= 1` and unique per occurrence | decimal string or `BigInt`; canonical decimal string |
| `configuration_lifecycle_events.event_sequence` | Deterministic event order within one configuration | 1 | PostgreSQL BIGINT maximum; no smaller semantic maximum | `event_sequence >= 1` and unique per configuration | decimal string or `BigInt`; canonical decimal string |

No JavaScript-number conversion is required or permitted for these fields.
The PostgreSQL driver preserves exact decimal text; `BigInt` or decimal-string
comparison is explicit at validation boundaries. No global PostgreSQL BIGINT
parser is installed. Truncation, clamping, rounding, and precision drift are
rejected, and canonicalization retains the exact integer value.

## 29. Migration design and ordering

The future RCV-020 migration is additive and runs after the existing frozen
RCV-009 through RCV-019 sequence. It creates enums, tables, constraints,
indexes, deferred overlap checks, and immutability triggers described here.

It must not alter prior RCV schema or semantics. A rollback plan may remove
only a never-used disposable migration in development; deployed historical
authority is not destructively rolled back.

## 30. Switzerland pilot

Swiss sources enter as LogicalSource, Monitor, and configuration data. The
same schema supports federal and cantonal authorities, courts, parliamentary
sources, statistical authorities, public institutions, and scientific feeds.
No Swiss-specific table, enum, or schema rule is required.

## 31. Security boundary

Adapters receive endpoint allowlists and policy limits from immutable
configuration. They enforce SSRF prevention, redirect validation, payload size
limits, parser isolation, credential-reference protection, and source
rate-limit policy before Capture creation.

Account/login security, permissions, DDoS protection, and generic application
abuse controls remain outside RCV-020.

## 32. Current-state independence and RCV-019 handoff

Historical verification binds only to persisted RCV-020 records and
authenticated retained artifacts. It does not use current source pages,
endpoints, configurations, adapters, parsers, or live availability state.

The integrated handoff is:

`ObservationOccurrence → RetrievalAttempt → Capture → AuthenticatedHandoff →
downstream evidence ingestion → later RCV-019 evolution`.

RCV-020 never directly mutates RCV-019. Downstream ingestion preserves Capture,
source, configuration, observation, and hash identities when creating evidence
authority.

## 33. Future RCV-021 compatibility

Research Orchestration may create new external or operator occurrences and
triggers that reference existing immutable Capture/Occurrence authority.
Search results become authoritative only after re-entering the normal
ObservationOccurrence → RetrievalAttempt → Capture path. No active-research
semantics are defined here.

## 34. Test and proof plan

Later proof waves must include:

- Wave 1: migration, constraints, indexes, trigger, and static invariant
  verification;
- Wave 2: canonical/hash, lifecycle, occurrence/attempt/capture, terminal
  resolution, empty, and comparison semantics;
- Wave 3: write verification, transaction rollback, duplicate behavior, and
  concurrency;
- Wave 4: independent read verification, corruption/no-repair, retention
  history, and current-state independence;
- Wave 5: full physical Observatory flow, coverage, quarantine, retention,
  handoff, Swiss pilot simulation, soak, fuzz, and stress.

Proofs must use fresh disposable databases, exact migrations, deterministic
fixtures, persisted projections, repeated reads, and explicit cleanup. No
proof may use a retained database or treat skipped execution as pass.

## 35. Historical independent verification checklist

For every authoritative entity, a future verifier can authenticate the record
from persisted identity, parent relationships, canonical/hash fields, version
authority, lifecycle/retention events, and retained object hash when
replayability is asserted. If the raw object is unavailable, the verifier can
still authenticate the historical observation statement from immutable Capture
identity, metadata, canonical/hash, content hash, byte length, original
object/reference authority where applicable, and append-only availability
history, but reports REPLAYABLE false. Retained raw bytes are therefore not a
requirement for metadata/hash historical authentication.

## 36. Design self-audit

- Contract hash guard: required hash is recorded above and must be checked.
- Contract modification: none permitted or performed by this Design.
- New semantics: none; concrete tables and mechanics implement Contract
  meanings.
- Mutable historical authority: prohibited by append-only rows and triggers.
- Current-state substitution/fallback: prohibited.
- Silent repair: prohibited.
- Truth/trust/reputation leakage: prohibited.
- RCV-019 violation: none; handoff is downstream and append-only.
- Switzerland: data-only.
- RCV-021: future scope only.

This Design is ready for review, not for migration or implementation until
approved.
